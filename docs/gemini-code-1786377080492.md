# IndepAssoc — Continuous Outcome Family Fix & Sparse Factor Table Handling

> Working spec for OpenCode. Follow phase by phase, strictly in order.
> Do not bump the package version or tag a release. Ensure all changes
> maintain strict backward compatibility.

## Context

During test execution of `IndepAssoc` v0.6.0, two runtime bugs were
identified:

1.  **Continuous Outcomes Crash in
    [`run_pipeline()`](https://mostafa-abbas.github.io/IndepAssoc/reference/run_pipeline.md)
    /
    [`fit_all_models()`](https://mostafa-abbas.github.io/IndepAssoc/reference/fit_all_models.md):**
    - **Symptom:**
      `Error in eval(family$initialize) : y values must be 0 <= y <= 1`
      inside `glm(...)`.
    - **Root Cause:**
      [`fit_all_models()`](https://mostafa-abbas.github.io/IndepAssoc/reference/fit_all_models.md)
      hardcodes `family = "binomial"` (or passes `family = "binomial"`
      down regardless of outcome type) when fitting the baseline
      multi-variable regression models in
      [`run_pipeline()`](https://mostafa-abbas.github.io/IndepAssoc/reference/run_pipeline.md).
    - **Fix:** Dynamically determine GLM family based on outcome
      distribution (`family = binomial()` for binary 0/1 outcomes;
      `family = gaussian()` or [`lm()`](https://rdrr.io/r/stats/lm.html)
      for continuous outcomes like length of stay).
2.  **Sparse Categorical Factor Errors during Matched Table 1
    Generation:**
    - **Symptom:** `add_p()` error during `tbl_summary()` on matched
      datasets:
      `For variable 'cat2': 'x' and 'y' must have the same number of levels (minimum 2)`.
    - **Root Cause:** Nearest-neighbor 1:1 matching can drop
      low-frequency factor levels in sparse categorical covariates
      (e.g., rare primary diagnosis categories). When
      [`gtsummary::add_p()`](https://www.danieldsjoberg.com/gtsummary/reference/add_p.html)
      runs on the matched table, variables with only 1 level in either
      exposure arm cause `add_p()` to fail.
    - **Fix:** Pre-screen matched covariates to drop zero-variance /
      single-level factors before generating matched summary tables, or
      wrap the `add_p()` call in a graceful
      [`tryCatch()`](https://rdrr.io/r/base/conditions.html) block so
      table generation degrades gracefully without halting the pipeline.

## Phase 27 — Code Fix: Continuous Outcome Model Family Dispatch in `fit_all_models()`

### Objective

Ensure continuous outcomes (`outcome_type = "continuous"` or
auto-detected continuous vector) are fit using
[`gaussian()`](https://rdrr.io/r/stats/family.html) / linear models
across all internal step functions in
[`run_pipeline()`](https://mostafa-abbas.github.io/IndepAssoc/reference/run_pipeline.md).

### Execution Steps

1.  Create a dedicated branch or worktree:
    `fix/continuous-outcome-family`.
2.  **Write a failing test first:**
    - Add a unit test in `tests/testthat/test-run_pipeline.R` executing
      [`run_pipeline()`](https://mostafa-abbas.github.io/IndepAssoc/reference/run_pipeline.md)
      on `rhc_sample` using a continuous outcome (e.g.,
      `outcome = "los"`). Assert that it completes without throwing
      `y values must be 0 <= y <= 1`.
3.  **Implement the fix:**
    - Inspect `R/fit_all_models.R` (or whichever internal R script
      defines model fitting inside
      [`run_pipeline()`](https://mostafa-abbas.github.io/IndepAssoc/reference/run_pipeline.md)).
    - Detect whether the outcome variable is binary ($`y \in \{0, 1\}`$)
      or continuous.
    - Pass `family = binomial()` for binary outcomes and
      `family = gaussian()` (or use
      [`lm()`](https://rdrr.io/r/stats/lm.html)) for continuous
      outcomes.
4.  **Verify:**
    - Run
      [`devtools::test()`](https://devtools.r-lib.org/reference/test.html)
      to ensure all tests pass.
    - Confirm binary outcome results (`dth30`, `death`) remain
      numerically identical to v0.6.0 defaults.

## Phase 28 — Code Fix: Robust Handling of Sparse Categorical Covariates in Matched Summary Tables

### Objective

Prevent
[`gtsummary::add_p()`](https://www.danieldsjoberg.com/gtsummary/reference/add_p.html)
or Table 1 generation from throwing unhandled exceptions when
propensity-score matching drops rare factor levels.

### Execution Steps

1.  Create a dedicated branch or worktree:
    `fix/sparse-factor-table-summary`.
2.  **Write a failing test first:**
    - Create a synthetic dataset or use `rhc_sample` with a deliberately
      sparse factor covariate (e.g., a factor where 1 level has only 1
      observation). Run
      [`run_pipeline()`](https://mostafa-abbas.github.io/IndepAssoc/reference/run_pipeline.md)
      and assert that Table 1 generation completes without halting the
      pipeline.
3.  **Implement the fix:**
    - Locate the function building matched `tbl_summary` tables (e.g.,
      Step 5/9 in
      [`run_pipeline()`](https://mostafa-abbas.github.io/IndepAssoc/reference/run_pipeline.md)).
    - Before executing `add_p()`, inspect factor levels across exposure
      groups in the matched subset. If a factor variable has $`<2`$
      levels present in any exposure group, either exclude that specific
      variable from `add_p()` testing or wrap `add_p()` in
      [`tryCatch()`](https://rdrr.io/r/base/conditions.html).
4.  **Verify:**
    - Run
      [`devtools::test()`](https://devtools.r-lib.org/reference/test.html).
    - Confirm pipeline returns complete results without error on
      `rhc_sample`.
